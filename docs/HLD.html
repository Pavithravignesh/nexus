Nexus Architecture
High-level design · nexus

How Nexus is built: one simulator, one stream, a store outside React

A real-time operations dashboard for 10,000 simulated devices with 10 sensors each. The server keeps the whole fleet in memory and pushes changes once per second. Each browser tab keeps its own copy, updated from that stream.

Next.js 16 · App Router TypeScript strict Server-Sent Events, 1 Hz zod at every boundary MongoDB (optional) three.js · D3

100,000 docs

One per device and sensor. Upserted every 5 s for the devices that changed, so it never grows.

  "deviceId": "DEV-00042",
  "sensor": "co2",

REFKey design decisions

SSE, not WebSockets

Data flows one way, server to browser. EventSource reconnects by itself and it is plain HTTP. Actions use ordinary REST.

One simulator, one hub

Connections never own a timer. Each tick is serialised once, so ten tabs cost one JSON.stringify, not ten.

Deltas, not full frames

Only devices that reported or changed status are sent, about 10–15% of the fleet per second.

No React state for 10,000 devices

Typed arrays in a store outside React; components subscribe by topic or row, and renders batch once per animation frame.

Memory first, database second

Hot state lives in memory. MongoDB gets bulk writes every 5 seconds and the app keeps working if it is down.

zod at every boundary

Query strings, request bodies, API responses and every stream frame are validated, and server and browser share the schemas.
